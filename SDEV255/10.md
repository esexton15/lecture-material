# Part 1: Why Next.js and What It Changes

---

## Recap: Last Lecture's Architecture

What we built:

- `bbs-api/` — Express server on port 3001
- `bbs-client/` — React app on port 5173
- CORS middleware to allow cross-origin requests
- Manual view switching with `currentView` state
- Separate `package.json` files, separate installs, separate builds

This worked. But it introduced friction:

- Two projects to maintain
- CORS configuration (easy to forget)
- No real URL routing (the URL never changes when you navigate)
- Two build processes and two deployments

<!--
Lecture notes:
- Ask students what felt awkward about yesterday's setup.
- CORS and manual view switching are usually the top answers.
-->

## What Next.js Offers

Next.js is a **fullstack React framework** that combines frontend and backend in one project.

What changes:

| Yesterday (MERN)          | Today (Next.js)                |
| ------------------------- | ------------------------------ |
| Two projects              | One project                    |
| Two dev servers           | One dev server                 |
| CORS configuration        | Not needed (same origin)       |
| Manual view state         | File-system routing (real URLs)|
| Separate deployments      | Single deployment              |

What stays the same:

- React components and JSX
- useState, useEffect, props
- Fetch patterns and error handling
- RESTful API design

<!--
Lecture notes:
- Emphasize: the React skills transfer directly.
- Next.js changes the plumbing, not the UI code.
-->

---

## Key Next.js Concepts

**App Router** (modern approach):

- The `app/` directory defines your routes
- Folders become URL paths
- `page.js` files are the entry points for each route

**File-system routing**:

```
app/
  page.js            → /
  posts/
    page.js          → /posts
    [id]/
      page.js        → /posts/5
```

No router library needed. The folder structure IS the routing.

Lecture notes:
- Draw this folder tree on screen.
- Compare to yesterday's manual currentView state switching.
- Ask: "What URL would app/about/page.js create?"
-->

## Server Components vs Client Components

This is the biggest new concept in Next.js.

**Server Components** (default):

- Run on the server, not in the browser
- Can fetch data directly (no useEffect needed)
- Cannot use useState, useEffect, or event handlers
- Smaller JavaScript sent to the browser

**Client Components** (opt-in with `"use client"`):

- Run in the browser, just like regular React
- Can use useState, useEffect, event handlers
- Marked with `"use client"` at the top of the file

Rule of thumb: if it has interactivity, it needs `"use client"`.

<!--
Lecture notes:
- This is the mental shift students need to make.
- Start simple: pages that just display data = Server Components.
- Forms, buttons, state = Client Components.
-->

---

## Server Component Example

A page that fetches and displays posts — no useState, no useEffect:

```jsx
// app/page.js (Server Component — no "use client")
async function PostListPage() {
  const res = await fetch("http://localhost:3000/api/posts");
  const posts = await res.json();

  return (
    <div>
      <h1>Bulletin Board</h1>
      {posts.map((post) => (
        <div key={post.id}>
          <h2>{post.title}</h2>
          <p>By {post.author} — {post.replyCount} replies</p>
        </div>
      ))}
    </div>
  );
}

export default PostListPage;
```

The fetch happens on the server. The browser receives rendered HTML.

<!--
Lecture notes:
- Compare this to yesterday's PostList with useEffect.
- Point out: no loading state needed for the initial render (server waits for data).
- The browser gets the final HTML, not a loading spinner.
-->

---

## Client Component Example

A form with state and event handlers needs `"use client"`:

```jsx
// components/NewPostForm.jsx
"use client";

import { useState } from "react";

export default function NewPostForm({ onPostCreated }) {
  const [title, setTitle] = useState("");
  // ... more state and handlers

  return (
    <form onSubmit={handleSubmit}>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      {/* ... */}
    </form>
  );
}
```

You can import Client Components into Server Components. They mix in the same app.

<!--
Lecture notes:
- Emphasize: "use client" is a file-level directive, not a component-level one.
- Everything in that file becomes a Client Component.
-->

---

## When to Use Which

| Use Server Component when         | Use Client Component when          |
| --------------------------------- | ---------------------------------- |
| Displaying data from an API       | Handling form input (useState)     |
| No user interaction needed        | Responding to clicks (onClick)     |
| Fetching on page load             | Using useEffect                    |
| Layout and page structure         | Real-time updates                  |

Most pages are Server Components that import small Client Components for interactivity.

<!--
Lecture notes:
- The pattern is: Server Component page + Client Component form/button.
- This is the default architecture in modern Next.js.
-->

## Tradeoffs

**Next.js advantages:**

- One project, one deploy
- No CORS (same origin)
- Built-in routing (file-system)
- Server Components reduce client JavaScript
- Built-in loading states
- SEO-friendly (server-rendered HTML)

**Next.js costs:**

- More abstraction and "magic"
- Server vs Client Component mental model
- Framework lock-in (harder to migrate away)
- Opinionated structure (less flexibility)

Neither approach is universally better. The right choice depends on the project and team.

<!--
Lecture notes:

- The patterns (REST, React, fetch) matter more than the framework.
-->

## API Routes (Route Handlers)

Next.js API routes live inside `app/api/` and use standard HTTP patterns.

The structure mirrors REST endpoints:

```
app/api/posts/route.js         → GET /api/posts, POST /api/posts
app/api/posts/[id]/route.js    → GET /api/posts/:id, DELETE /api/posts/:id
app/api/posts/[id]/replies/route.js → POST /api/posts/:id/replies
```

Each `route.js` exports named functions for HTTP methods:

```javascript
// GET handler
export async function GET(request) { ... }

// POST handler
export async function POST(request, { params }) { ... }

// DELETE handler
export async function DELETE(request, { params }) { ... }
```

Same REST patterns as yesterday's Express routes. Different syntax.

<!--
Lecture notes:
- Compare to yesterday's Express routes side by side.
- Express: app.get("/api/posts", handler)
- Next.js: export async function GET() in app/api/posts/route.js
- Emphasize: same logic, different file organization.
-->

## NextResponse vs Express res

Yesterday (Express):

```javascript
app.get("/api/posts", (req, res) => {
  res.json(posts);
});
```

Today (Next.js):

```javascript
import { NextResponse } from "next/server";

export async function GET() {
  return NextResponse.json(posts);
}
```

`NextResponse.json()` replaces `res.json()`. Same result, different object.

<!--
Lecture notes:
- Show both side by side.
- The request/response concepts are identical.
- Next.js uses Web standard Request/Response objects instead of Express's custom ones.
-->

---

## Reading Request Data

Yesterday (Express):

```javascript
app.post("/api/posts", (req, res) => {
  const { title, body, author } = req.body;
});
```

Today (Next.js):

```javascript
export async function POST(request) {
  const body = await request.json();
  const { title, body: postBody, author } = body;
}
```

The Web Request object has a `.json()` method. Same data, different API.

<!--
Lecture notes:
- Point out: request.json() returns a Promise, so we await it.
- Express uses middleware (express.json()) to parse the body.
- Next.js parses it automatically.
-->

## Route Parameters

Yesterday (Express):

```javascript
app.get("/api/posts/:id", (req, res) => {
  const id = parseInt(req.params.id);
});
```

Today (Next.js):

```javascript
export async function GET(request, { params }) {
  const id = parseInt(params.id);
}
```

`params` is the second argument to the handler function. It contains all dynamic route segments.

<!--
Lecture notes:

- If the route was [id]/replies, params would be { id: "5" }.

## The Link Component

Next.js provides `<Link>` for client-side navigation:


## Adding Client Components for Interactivity

Server Components cannot have forms or event handlers. Import Client Components for those parts.

```jsx
// app/posts/[id]/page.js (Server Component)
import ReplyForm from "@/components/ReplyForm";

export default async function PostDetailPage({ params }) {
  const post = await fetchPost(params.id);

  return (
    <div>
      {/* server-rendered content */}
      <h1>{post.title}</h1>
      <p>{post.body}</p>

      {/* client component for interactivity */}
      <ReplyForm postId={post.id} />
    </div>
  );
}
```

Server Components and Client Components mix seamlessly in the same page.

<!--
Lecture notes:
- The pattern: Server Component page fetches data, passes it to Client Components for interaction.
- ReplyForm needs useState and handleSubmit, so it must be a Client Component.

## ReplyForm (Client Component)

```jsx
// components/ReplyForm.jsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";

export default function ReplyForm({ postId }) {
  const [body, setBody] = useState("");
  const [author, setAuthor] = useState("");
  const router = useRouter();

  async function handleSubmit(e) {
    e.preventDefault();
    await fetch(`/api/posts/${postId}/replies`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ body, author }),
    });
    router.refresh(); // re-fetch server data
    setBody("");
    setAuthor("");
  }

  return (
    <form onSubmit={handleSubmit}>
      {/* inputs */}
    </form>
  );
}
```

`router.refresh()` re-runs the Server Component's fetch and updates the page.

<!--
Lecture notes:
- The fetch URL is relative: /api/posts/${postId}/replies (no localhost needed).
- router.refresh() is the key Next.js feature: it re-fetches server data without a full navigation.
- Compare to yesterday: we had to manually re-fetch with useEffect after creating a reply.
-->

## useRouter for Navigation

Next.js provides `useRouter` for programmatic navigation:

```jsx
import { useRouter } from "next/navigation";

const router = useRouter();

router.push("/")       // navigate to home
router.push("/posts/5") // navigate to post detail
router.refresh()       // re-fetch current page data
router.back()          // go back in history
```

Use `<Link>` for declarative navigation in JSX. Use `router.push()` after form submissions or other actions.

<!--
Lecture notes:

- router.push() updates the real URL. setView() did not.

```jsx
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <p>Loading...</p>;

  return posts.map(post => (
    <div onClick={() => onSelectPost(post.id)}>
      <h2>{post.title}</h2>
    </div>
  ));
}
```

**Today (Next.js):**

```jsx
async function PostListPage() {
  const posts = await fetch("http://localhost:3000/api/posts").then(r => r.json());

  return posts.map(post => (
    <Link href={`/posts/${post.id}`}>
      <h2>{post.title}</h2>
    </Link>
  ));
}
```

Same result. Less code. No useState, no useEffect, no loading state.

## When to Use Each Approach

**Choose traditional MERN when:**

- You want maximum flexibility in tooling
- Frontend and backend teams work independently
- You might swap the frontend framework later
- You are building microservices
- You need fine-grained control over the server

**Choose Next.js when:**

- You want developer productivity and simplicity
- Your team is all-React
- You need SEO (server-rendered HTML)
- You want built-in routing and loading states
- You prefer one project and one deployment

Neither is universally better. Good developers understand both.

## What Happens When Databases Are Added

Both approaches connect to databases the same way on the server side.

What changes:

- In-memory array becomes database queries
- Helper functions in `lib/data.js` become model functions that call a database
- The one-to-many relationship (posts → replies) becomes a database relation

What stays the same:

- React components and JSX
- API endpoint URLs and HTTP methods
- Fetch patterns in the frontend
- Status codes and error handling

When we cover databases, you replace the data layer. Everything else stays.

## Key Takeaways

- **Traditional MERN** and **Next.js** produce the same result with different plumbing
- **Server Components** fetch data on the server, reducing client-side complexity
- **File-system routing** replaces manual view state management
- **CORS** is only needed when frontend and backend are on different origins
- **The patterns** (REST, React, fetch, state) matter more than the framework
- **Both approaches** are valid — choose based on project and team needs

A fullstack developer understands the patterns and can work in any stack.
