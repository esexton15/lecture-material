# Part 1: Object Model Design

---

## What OOP Means in This Course

Object-oriented programming groups:

- data into objects
- behavior into methods
- rules into the same model that owns the data

Instead of scattering logic everywhere, we let an object manage its own state.

---

## Class vs Object vs Instance

- Class: blueprint for creating objects
- Object: one concrete value in memory
- Instance: an object created from a class

Example:

- `Task` is a class
- `new Task("Pay bill")` creates one instance

---

## Why Use Classes Here?

For this mini-app, a class helps us:

- keep task data together
- attach behavior like `toggleDone()` and `label()`
- prevent invalid values from spreading through the app
- make DOM and validation code easier to organize

---

## The `this` Keyword in Classes

`this` refers to the current object instance.

Inside `label()`, `this.title` means "the title for this specific task object."

- `this` helps one method work for many different task objects
- each instance keeps its own state

---

## Core OOP Ideas We Will Use

- Encapsulation: keep data and rules together
- Abstraction: expose useful methods, hide internal details
- Inheritance: let one class build on another

We will focus mostly on encapsulation and clean object design in this lecture.

---

## Object Model with Data Security

What we are doing:

- creating a `Task` model for the mini-app
- storing title and priority inside the object
- making title go through a controlled write path

Why it matters:

- every task follows the same rules
- invalid data gets blocked at the model layer
- UI code no longer has to guess what is valid

---

## Accessor-Based Validation

What we are doing:

- reading title through a getter
- writing title through a setter
- trimming and validating input before saving it

Why it matters:

- validation happens automatically every time title changes
- the object protects itself from bad state
- we avoid duplicated validation logic in multiple handlers

---

## Why This Model Is Safer

- Private field `#title` blocks direct external writes
- Setter centralizes normalization and validation
- Invalid state is rejected early
- Methods expose controlled behavior, not raw mutation

This is the core of objective 2.

---

## Methods and Operators in App Logic

What we are adding:

- a method to toggle task completion
- a method to produce a display label
- simple operators inside class behavior

Why it matters:

- the object owns its own behavior
- UI code can ask for `task.label()` instead of rebuilding strings
- operators like `!` stay inside the model where the rule belongs

Uses functions, OOP methods, and operators.

---

## Object Method Style: Literal

What this shows:

- objects can have methods even without using a class
- a method is just a property whose value is a function
- `this` still refers to the current object

Use this style for small object literals and one-off grouped behavior.

---

## Object Method Style: Add After Creation

What this shows:

- behavior can be attached after an object already exists
- JavaScript objects are flexible and extensible

Why students should care:

- you will see this pattern in existing codebases
- it helps explain that methods are properties, not special syntax magic

---

## Constructor vs Prototype Methods

Prototype methods are memory efficient because all instances share one method implementation.

Why this matters conceptually:

- classes in JavaScript are built on prototypes
- shared methods do not need to be recreated for every object
- modern `class` syntax is cleaner, but this is the underlying model

---

## Encapsulation in Practice

Encapsulation means an object controls how its data changes.

In this lecture, that looks like:

- private field for protected state
- getter for safe reads
- setter for safe writes
- methods for approved behavior changes

This is the OOP idea most directly tied to data security.

---

## Inheritance: The Basic Idea

Inheritance lets one class reuse another class' properties or behavior.

Example idea:

- `Task` could be the base model
- `TimedTask` could extend `Task` and add a due date

You do not use inheritance everywhere, but it helps when one type is a more specific version of another.

# Part 2: Built-In Types and Strings

---

## Built-In Types Used in This Mini-App

- `String`: task title, priority
- `Boolean`: completion state, validity flags
- `Array`: list of tasks in memory
- `Object`: each task instance
- `Number`: optional counters and limits

Choosing types intentionally reduces bugs.

---

## String Handling for User Input

Common checks:

- `trim()`
- `length`
- `includes()`

Why these matter here:

- user input arrives as strings
- strings often need cleanup before validation
- normalization should happen before storing values in the object model

---

## Primitive vs Reference Behavior

Primitives copy values; objects copy references.

Design implication: only mutate object state through intentional APIs.

Why students need this idea:

- passing an object into a function can change the original object
- that is powerful, but also risky
- OOP design helps control where those changes are allowed

# Part 3: DOM with OOP Methodology

---

## OOP Separation for DOM Work

Use a simple role split:

- Model: `Task` class (data + rules)
- View: rendering object (DOM output)
- Controller: event handlers (workflow)

This keeps DOM code from polluting business logic.

---

## View Object Example

What the view is responsible for:

- locating the output area in the page
- creating display elements
- asking the model for the text it should show

Why this matters:

- the model does not need to know DOM details
- the DOM layer stays focused on presentation

---

## Controller Example (Submit Flow)

What the controller does:

- listens for submit event
- prevents default browser submit behavior
- gathers user input from form fields
- creates a `Task` object
- tells the view to render the result

This is the bridge between user actions, objects, and DOM output.

---

## Event-Driven Detail for DOM Work

Key event concepts used in this app:

- `input` for live field validation
- `submit` for final form gate
- `preventDefault()` to block invalid submit
- `event.target` to inspect source element

This is the practical OOP controller layer in browser code.

# Part 4: JSON and Data Management

---

## JSON Basics in This App

JSON is the transport format between browser and server.

- `stringify`: JS object -> JSON string
- `parse`: JSON string -> JS object

Why it matters:

- browsers and servers often exchange data as JSON
- JSON is readable by people and efficient for machines
- it is the boundary between app objects and transmitted data

---

## JSON Impact on Data Management

- JSON payloads are data-only (no methods)
- Class instances lose behavior when serialized
- Rebuild domain objects after parse when needed

Design implication: separate transport data from app objects.

---

## JSON Structure Rules and Pitfalls

JSON value types:

- String, Number, Object, Array, Boolean, `null`

Important rules:

- Object keys must be double-quoted strings
- Trailing commas are invalid JSON
- Use single quotes for JS strings containing JSON text when helpful

---

## Advanced JSON Controls

- Reviver transforms parsed values
- Replacer filters/transforms output
- Spacer formats readable JSON

Why these matter:

- reviver helps rebuild richer JavaScript values
- replacer lets you limit or customize what gets sent
- spacer makes debugging and teaching output easier to read

# Part 5: Form Validation in Application Flow

---

## Validation Strategy

Two layers:

1. Field-level validation while typing (`input` event)
2. Submit-time validation before sending data (`submit` event)

Always validate on server too.

---

## Field-Level Validation Example

What we are doing:

- listening while the user types
- checking the current input value immediately
- tracking whether the field is valid right now

Why it matters:

- user gets faster feedback
- invalid entries can be corrected before submit
- form logic becomes easier to reason about

---

## Submit Validation Example

Use `checked` for checkbox/radio validation.

What the submit handler is checking:

- whether required fields are valid
- whether required checkboxes are checked
- whether the form should be blocked from sending

---

## HTML Native Validation (Use It)

Use browser-native constraints first, then add JS for custom rules.

What native HTML gives you for free:

- required field enforcement
- min/max length rules
- regex pattern checks
- simple checkbox requirements

---

## Validation Checks to Apply Deliberately

Common checks in this module:

- `value.length` for min/max text length
- `===` for exact allowed values
- `indexOf()` / `includes()` for forbidden/required text
- `isNaN()` for numeric checks
- regex with `match()` or `test()` for pattern checks
- `checked` for checkbox/radio requirements

---

## Browser Validation Styling Hooks

Use CSS pseudo-classes for immediate visual cues:

- `:valid`
- `:invalid`
- `:required`
- `:optional`

This gives feedback without extra JavaScript complexity.
