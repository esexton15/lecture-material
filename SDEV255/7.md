# Part 1: What React Is and Why It Exists

---

## The Problem React Solves

Before React, UI code often looked like this:

1. Find element in DOM
2. Manually update element
3. Track state in variables scattered across code
4. Hope nothing gets out of sync

This is **imperative** programming: you tell the browser _how_ to do each step.

<!--
Lecture notes:
- Ask: "Who has written code like `document.getElementById` and manually updated innerHTML?"
- This is the pain point React addresses.
-->

---

## Declarative vs Imperative

**Imperative (what you've done):**

```javascript
const counter = document.getElementById("counter");
counter.textContent = count;
```

**Declarative (what React does):**

```javascript
function Counter({ count }) {
  return <div>{count}</div>;
}
```

You describe _what_ the UI should look like. React handles _how_ to update the DOM.

<!--
Lecture notes:
- Key phrase: "You describe the destination; React drives the car."
- This mental shift is the most important concept today.
-->

---

## Component-Based Architecture

A **component** is a reusable piece of UI.

- Components can contain other components
- Each component manages its own data and behavior
- Components are like functions: input in, UI out

Example mental model:

- `App` contains `Header`, `TaskList`, `Footer`
- `TaskList` contains many `TaskItem` components
- Each `TaskItem` shows one task

<!--
Lecture notes:
- Draw a simple tree on screen: App at top, children below.
- Compare to functions calling functions.
-->

---

## The Virtual DOM (Brief)

React keeps a copy of the UI in memory called the **Virtual DOM**.

When state changes:

1. React creates a new virtual DOM tree
2. Compares it to the previous version
3. Calculates the minimum DOM changes needed
4. Updates only what changed

You rarely think about this directly, but it's why React is fast.

<!--
Lecture notes:
- Keep this brief. Students don't need deep Virtual DOM knowledge yet.
- Just: "React optimizes DOM updates for you."
-->

React uses all of these. The new part:

# Part 2: JSX and Component Basics

---

## What is JSX?

JSX is a syntax extension for JavaScript that lets you write UI code that looks like HTML.

```jsx
function Greeting() {
  return <h1>Hello, React!</h1>;
}
```

Behind the scenes, JSX compiles to JavaScript:

```javascript
function Greeting() {
  return React.createElement("h1", null, "Hello, React!");
}
```

You write JSX; the tools translate it.

<!--
Lecture notes:
- Key point: JSX is not a template language; it's syntax sugar for JavaScript.
- You can put any JavaScript expression inside JSX with curly braces.
-->

---

## JSX Rules

1. **Return a single parent element** (or use Fragment `<>...</>`)
2. **Close all tags** (including `<img />`, `<br />`, `<input />`)
3. **Use camelCase for attributes** (`className`, `onClick`, `htmlFor`)
4. **JavaScript expressions go in curly braces** `{variable}`

```jsx
function Example() {
  const name = "Student";
  return (
    <div className="container">
      <h1>Hello, {name}!</h1>
      <img src="logo.png" alt="Logo" />
    </div>
  );
}
```

<!--
Lecture notes:
- Most common beginner error: returning multiple elements without wrapper.
- Second most common: using `class` instead of `className`.
-->

---

## Your First Component

A React component is a function that returns JSX.

```jsx
function App() {
  return (
    <div>
      <h1>Welcome to My App</h1>
      <p>This is my first React component.</p>
    </div>
  );
}
```

Convention: Component names start with uppercase. Functions that return JSX are components.

- Then modify the text and show the update.
-->

## Rendering to the DOM

To show your component, you render it into an HTML element.

```jsx
import { createRoot } from "react-dom/client";

function App() {
  return <h1>Hello, world!</h1>;
}

const container = document.getElementById("root");
const root = createRoot(container);
root.render(<App />);
```

Your HTML needs one element for React to render into:

```html
<div id="root"></div>
```

<!--
Lecture notes:

## Component Composition

Components can contain other components.

```jsx
function Header() {
  return (
    <header>
      <h1>My App</h1>
    </header>
  );
}

function Main() {
  return (
    <main>
      <p>Welcome to the main content.</p>
    </main>
  );
}

function Footer() {
  return (
    <footer>
      <p>© 2026 My App</p>
    </footer>
  );
}

function App() {
  return (
    <div>
      <Header />
      <Main />
      <Footer />
    </div>
  );
}
```

## Fragments: Invisible Containers

When you need to return multiple elements without adding extra DOM nodes:

```jsx
function List() {
  return (
    <>
      <li>First item</li>
      <li>Second item</li>
      <li>Third item</li>
    </>
  );
}
```

`<>...</>` is a **Fragment**. It groups elements without creating a wrapper div.

<!--
Lecture notes:
- Use this when showing a list inside a `<ul>` parent.
- Fragments keep the DOM clean.
-->

# Part 3: Props - Passing Data Down

---

## What Are Props?

**Props** (short for "properties") are how you pass data from a parent component to a child component.

Think of props like function arguments:

```jsx
function Greeting(props) {
  return <h1>Hello, {props.name}!</h1>;
}

// Usage:
<Greeting name="World" />;
```

Props flow **one direction**: parent to child.

<!--
Lecture notes:
- Draw an arrow from parent to child on screen.
- Emphasize: props are read-only in the child.
-->

---

## Destructuring Props

It's common to destructure props in the function signature:

```jsx
function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

// Multiple props:
function TaskItem({ title, priority }) {
  return (
    <div>
      <strong>{title}</strong> - {priority}
    </div>
  );
}
```

This makes it clear what data the component expects.

<!--
Lecture notes:
- Show both styles: `props.name` and destructured `{ name }`.
- Recommend destructuring for readability.
-->

---

## Props Are Read-Only

A component should never modify its own props.

```jsx
// BAD - Never do this
function Greeting({ name }) {
  name = name.toUpperCase(); // Don't modify props!
  return <h1>Hello, {name}</h1>;
}
```

Props come from the parent. The child receives them, displays them, but doesn't change them.

If you need data that changes, that's **state** (coming next part).

<!--
Lecture notes:
- This is a core React principle: props are immutable.
- It enables predictable data flow and easier debugging.
-->

---

## Passing Different Data Types

```jsx
function TaskCard({ title, isComplete, priority, tags }) {
  return (
    <div className="task-card">
      <h3>{title}</h3>
      <p>Status: {isComplete ? "Done" : "Pending"}</p>
      <p>Priority: {priority}</p>
      <p>Tags: {tags.join(", ")}</p>
    </div>
  );
}

// Usage:
<TaskCard
  title="Learn React"
  isComplete={false}
  priority={1}
  tags={["frontend", "learning"]}
/>;
```

Notice: non-string values use curly braces: `isComplete={false}`, `priority={1}`.

<!--
Lecture notes:
- Common mistake: passing `{false}` as string `"false"`.
- Show what happens when you pass a string vs boolean.
-->

---

## Passing Functions as Props

You can pass functions to children so they can communicate back up.

```jsx
function Button({ label, onClick }) {
  return <button onClick={onClick}>{label}</button>;
}

function App() {
  function handleClick() {
    alert("Button clicked!");
  }

  return <Button label="Click Me" onClick={handleClick} />;
}
```

The parent defines the behavior; the child triggers it.

<!--
Lecture notes:
- This pattern is everywhere in React.
- It enables "lifting state up" which we'll cover later.
-->

---

## Default Props

You can provide fallback values when props are missing:

```jsx
function Greeting({ name = "Guest" }) {
  return <h1>Hello, {name}!</h1>;
}

// Usage:
<Greeting />          // Hello, Guest!
<Greeting name="Amy" /> // Hello, Amy!
```

Default values make components more resilient.

<!--
Lecture notes:
- Show what happens without the default when prop is missing.
- Default props prevent "undefined" from appearing in your UI.
-->

# Part 4: State with useState

---

## What Is State?

**State** is data that can change over time and affects what the component renders.

Unlike props (which come from outside), state is managed **inside** the component.

When state changes, React re-renders the component automatically.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  // count is the current value
  // setCount is the function to update it
  // 0 is the initial value
}
```

<!--
Lecture notes:
- Compare to a variable: state triggers re-renders when it changes.
- Draw the cycle: initial render -> user action -> state change -> re-render.
-->

---

## The useState Hook

`useState` is a **hook** - a function that lets you "hook into" React features.

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}
```

The array destructuring `[count, setCount]` gives you:

- `count`: the current state value
- `setCount`: the function to update state

<!--
Lecture notes:
- Write this live. Show the counter incrementing.
- Then try to modify state directly and show it doesn't work.
-->

---

## State Updates Trigger Re-renders

When you call `setCount(newValue)`:

1. React updates the state value
2. React re-runs your component function
3. React updates the DOM with the new JSX

This is why your UI stays in sync with your data.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  console.log("Component rendered, count is:", count);
  // This logs every time state changes!
}
```

<!--
Lecture notes:
- Show the console log to prove re-renders happen.
- This is a key debugging technique.
-->

---

## Never Modify State Directly

**Wrong:**

```jsx
count = count + 1; // This won't trigger a re-render!
```

**Correct:**

```jsx
setCount(count + 1); // This triggers a re-render
```

State must be updated through the setter function. Direct assignment breaks React's change detection.

<!--
Lecture notes:
- Live demo: try both approaches and show which one works.
- This is the #1 beginner mistake with state.
-->

---

## Immutable State Updates for Objects and Arrays

When state is an object or array, you must create a new copy:

**Wrong:**

```jsx
const [user, setUser] = useState({ name: "Alice" });
user.name = "Bob"; // Mutating directly!
setUser(user); // Won't detect the change
```

**Correct:**

```jsx
setUser({ ...user, name: "Bob" }); // New object with spread
```

For arrays:

```jsx
const [items, setItems] = useState([1, 2, 3]);
setItems([...items, 4]); // Add item
setItems(items.filter((i) => i !== 2)); // Remove item
```

<!--
Lecture notes:
- This is critical for the task app we'll build.
- Show what happens when you mutate directly (UI doesn't update).
-->

---

## Multiple State Variables

A component can have multiple state variables:

```jsx
function Form() {
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");
  const [isSubmitting, setIsSubmitting] = useState(false);

  return (
    <form>
      <input value={name} onChange={(e) => setName(e.target.value)} />
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      <button disabled={isSubmitting}>Submit</button>
    </form>
  );
}
```

<!--
Lecture notes:
- Each piece of state is independent.
- We'll cover forms in detail in Lecture 2.
-->

---

## State vs Props Summary

| Props                          | State                         |
| ------------------------------ | ----------------------------- |
| Passed from parent             | Managed inside component      |
| Read-only                      | Can be changed with setter    |
| External input                 | Internal data                 |
| Changes when parent re-renders | Changes when setter is called |

Use props for data that comes from outside. Use state for data that the component owns.
