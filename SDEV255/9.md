## The Fullstack Request Lifecycle

You have seen both halves. Today we connect them.

1. React component triggers `fetch()`
2. Request travels over HTTP to Express
3. Express route matches the URL and method
4. Controller reads request, calls model logic
5. Model returns data (from in-memory store)
6. Controller sends JSON response
7. React receives response, updates state, re-renders

One user action now crosses the entire application.

## The "ERN" Stack

MERN = **M**ongoDB + **E**xpress + **R**eact + **N**ode

Today we build the **ERN** part:

- Express handles API routes and business logic
- React handles the UI, state, and user interaction
- Node runs both

We skip MongoDB because databases are a future module. Our data lives in an in-memory array on the server.

Same architecture, same patterns. The data layer swaps in later.

## Two Projects, Two Servers

Traditional fullstack architecture uses separate projects:

```
bbs-api/          bbs-client/
  server.js         src/
  package.json        App.jsx
  node_modules/       components/
                      api/
                    package.json
                    node_modules/
```

- `bbs-api/` runs Express on port 3001
- `bbs-client/` runs Vite dev server on port 5173
- Two terminal tabs, two `npm start` commands

This separation is how many real teams work: frontend team and backend team, independent deployments.

## RESTful Endpoint Design

REST uses **nouns** for resources and **HTTP methods** for actions.

| Method | Endpoint                 | Action         |
| ------ | ------------------------ | -------------- |
| GET    | `/api/posts`             | List all posts |
| GET    | `/api/posts/:id`         | Get one post   |
| POST   | `/api/posts`             | Create a post  |
| POST   | `/api/posts/:id/replies` | Add a reply    |
| DELETE | `/api/posts/:id`         | Delete a post  |

Notice the nested route: `/api/posts/:id/replies`. Replies belong to a specific post.

<!--
Lecture notes:
- Emphasize: the URL describes the resource, the method describes the action.
- The nested route is the key new pattern today.
- Ask: "Why is the reply endpoint under /posts/:id and not just /replies?"
-->

---

## API Response Shaping

Different views need different data.

**List endpoint** returns summaries (no full replies):

```json
{
  "id": 1,
  "title": "Welcome",
  "author": "Alice",
  "createdAt": "2026-04-13T12:00:00Z",
  "replyCount": 3
}
```

<!--
Lecture notes:
- This is a real-world pattern: list views return summaries, detail views return full data.
- Ask: "Why would sending all replies in the list be wasteful?"
-->

---

**Detail endpoint** returns full data with replies:

```json
{
  "id": 1,
  "title": "Welcome",
  "author": "Alice",
  "body": "Hello everyone!",
  "createdAt": "2026-04-13T12:00:00Z",
  "replies": [...]
}
```

The list does not need every reply body. Sending only what the view needs keeps responses fast.

<!--
Lecture notes:
- This is a real-world pattern: list views return summaries, detail views return full data.
- Ask: "Why would sending all replies in the list be wasteful?"
-->

## What Is CORS?

**CORS** = Cross-Origin Resource Sharing.

Browsers block requests from one origin (port 5173) to another origin (port 3001) by default. This is a security feature.

Without CORS:

- React on `localhost:5173` tries to fetch `localhost:3001/api/posts`
- Browser blocks the request
- Console shows a CORS error

With the `cors` middleware on Express:

- Express adds headers that tell the browser "this is allowed"
- The request succeeds

CORS only matters when frontend and backend are on different ports or domains.

## Express API: Status Code Recap

Use status codes that match the outcome:

| Code | Meaning      | When to Use                 |
| ---- | ------------ | --------------------------- |
| 200  | OK           | Successful GET, PUT, DELETE |
| 201  | Created      | Successful POST             |
| 400  | Bad Request  | Missing or invalid input    |
| 404  | Not Found    | Resource does not exist     |
| 500  | Server Error | Unexpected server failure   |

Status codes are part of your API contract. Clients depend on them.

## API Service Layer

Keep fetch logic out of components. Create a separate file.

```javascript
// api/posts.js
const API_URL = "http://localhost:3001/api/posts";

export async function getAllPosts() {
  const res = await fetch(API_URL);
  if (!res.ok) throw new Error("Failed to fetch posts");
  return res.json();
}

export async function getPost(id) {
  const res = await fetch(`${API_URL}/${id}`);
  if (!res.ok) throw new Error("Post not found");
  return res.json();
}

export async function createPost(data) {
  const res = await fetch(API_URL, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(data),
  });
  if (!res.ok) throw new Error("Failed to create post");
  return res.json();
}
```

Same fetch patterns from Lectures 5 and 8. The only difference: the URL points to your own server.

## Client-Side Navigation Without a Router

We have two views: post list and post detail.

Instead of adding React Router, use state to switch views:

```javascript
function App() {
  const [view, setView] = useState({ type: "list" });
  // view can be:
  //   { type: "list" }
  //   { type: "detail", postId: 5 }
  //   { type: "new" }

  if (view.type === "detail") {
    return (
      <PostDetail
        postId={view.postId}
        onBack={() => setView({ type: "list" })}
      />
    );
  }

  return (
    <div>
      <PostList
        onSelectPost={(id) => setView({ type: "detail", postId: id })}
      />
    </div>
  );
}
```

This is conditional rendering (Lecture 8) applied to whole views.

## Component Data Flow

```
App
├── view = "list"
│   ├── PostList (fetches all posts)
│   │   └── [PostListItem] (clickable)
│   └── NewPostForm (creates post, navigates to list)
│
└── view = "detail"
    ├── PostDetail (fetches one post by id)
    │   ├── ReplyList (renders replies)
    │   └── ReplyForm (adds reply, re-fetches post)
    └── DeletePostButton (deletes, navigates to list)
```

App owns the view state. Components receive props and call service functions.

This is the **lifting state up** pattern from Lecture 8.

## The Full Round Trip

1. User clicks "New Post" in React
2. React renders the NewPostForm component
3. User fills in title, body, author and submits
4. React calls `createPost()` in the service layer
5. Service layer sends POST to `http://localhost:3001/api/posts`
6. Express receives the request, validates, creates the post
7. Express returns 201 with the new post JSON
8. React receives the response, navigates to the list view
9. PostList fetches all posts from the API
10. The new post appears in the list

One user action. Two servers. One result.

## Architecture Recap

What each part owns:

| Layer      | Responsibility                               |
| ---------- | -------------------------------------------- |
| React UI   | Rendering, user interaction, view navigation |
| Service    | Fetch calls, error handling, URL management  |
| Express    | Route matching, validation, business logic   |
| Data store | In-memory array (future: database)           |

The boundaries are clean. Each layer can be tested and changed independently.

## Key Takeaways from Today

- **CORS** is required when frontend and backend are on different origins
- **Nested resources** (`/posts/:id/replies`) model real data relationships
- **Response shaping** — list views and detail views can return different data shapes
- **Service layer** keeps fetch logic separate from component logic
- **View state** in App can replace a router for simple navigation
- **Status codes** are part of the API contract — React depends on them

These patterns transfer to any fullstack project, regardless of framework.
