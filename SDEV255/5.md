- Predictable rendering updates

Outcome: faster development and fewer UI consistency bugs.

# Part 1B: Using Third-Party Web APIs (3.2)

---

## API Integration Mindset

Client-side API work should answer:

- What endpoint is called?
- What request shape is required?
- What response shape is expected?
- How should errors/timeouts appear to users?

API integration is a user-experience problem, not just a network call.

<!--
Lecture notes:
- Ask class: "What does bad API UX feel like to users?"
- Pull one or two examples (spinners forever, vague errors).
-->

---

## API Contract Thinking

Before writing code, define:

- Request URL and method
- Required query/body parameters
- Expected success response shape
- Error response behavior

Treat API contracts as part of app design, not an afterthought.

<!--
Lecture notes:
- Emphasize contract-first thinking prevents rework.
- Phrase to repeat: "No contract, no stable UI."
-->

---

## Dynamic and Progressive Enhancements

Progressive enhancement means:

- Base page works first
- JavaScript enhances behavior when available

Dynamic enhancements include:

- Live filtering
- Loading indicators
- Inline validation and status messages
- Partial updates without full page reload

<!--
Lecture notes:
- Clarify progressive enhancement in one sentence: baseline works, JS improves it.
- Tie to accessibility and reliability.
-->

---

## Client-Side Architecture Pattern

Recommended structure:

- `components/` for UI units
- `services/` for API calls
- `state/` for shared app state
- `utils/` for formatting and reusable helpers

Keep API code out of view components when possible.

---

## API Call Lifecycle

1. User action triggers request
2. UI enters loading state
3. Request sent to API
4. Response parsed and validated
5. UI state updated
6. Error or success feedback rendered

This predictable cycle improves debuggability and UX.

<!--
Lecture notes:
- Walk the cycle as a narrated story from user click to UI update.
- This slide is the anchor for the later live build.
-->

---

## Client Error-Handling Expectations

Handle at least three error classes:

- Network failure (offline, timeout)
- Server failure (500 range)
- Data mismatch (unexpected response shape)

Never leave users with a silent failure.

# Part 2: WebSockets (3.3)

---

## Where WebSockets Fit

HTTP Fetch pattern:

- Client sends request
- Server sends response
- Connection ends

WebSocket pattern:

- Persistent connection
- Server can push updates anytime
- Better for live updates/chat/streaming dashboards

<!--
Lecture notes:
- Use contrast framing: "Fetch pulls, WebSockets push."
- Keep it conceptual today; no protocol deep dive.
-->

---

## WebSocket Tradeoffs

Benefits:

- Low-latency updates
- Real-time collaboration patterns

Costs:

- More stateful complexity
- Connection management overhead
- Different scaling considerations than stateless HTTP

<!--
Lecture notes:
- Ask: "Would you choose this for a simple search form? Why or why not?"
-->

---

## When to Choose Fetch vs WebSockets

Choose Fetch when:

- User-triggered operations dominate
- Request-response fits the feature

Choose WebSockets when:

- App needs frequent live updates
- Server-initiated pushes are required

Many apps use both patterns together.

<!--
Lecture notes:
- Give a quick real-world pair: dashboard (WebSocket) + settings form (Fetch).
-->

# Part 3: Promises (3.4)

---

## Why Promises Matter

Promises represent eventual completion/failure of async work.

They help avoid callback nesting and make flow easier to reason about:

- pending -> fulfilled / rejected
- chainable with `.then()` / `.catch()`
- clearer error propagation for async operations

<!--
Lecture notes:
- Connect to prior pain point: callback nesting and scattered error handling.
-->

## Promise Flow in UI Features

Typical pattern:

1. Start request
2. Handle success data
3. Handle failure state
4. Finalize UI state (loading off)

A predictable async pattern reduces fragile UI behavior.

<!--
Lecture notes:
- Tie this back to earlier API lifecycle slide: same flow, different async abstraction.
-->

---

## Promise Error-Handling Strategy

Good practice:

- Handle expected API failures explicitly
- Provide user-friendly error states
- Keep technical details in logs, not user messages
- Avoid swallowing errors silently

# Part 4: async and await (3.5)

---

## Why async/await Improves Readability

`async/await` is syntax on top of Promises.

It keeps asynchronous code closer to synchronous reading order:

- easier to follow business flow
- simpler try/catch error handling
- less chaining noise in complex logic

<!--
Lecture notes:
- Phrase: "Same Promise engine, cleaner syntax."
-->

---

## async/await Error Pattern

Use a `try/catch` structure around awaited calls.

Design guideline:

- keep await blocks focused
- return normalized values from service layer
- convert raw API errors into user-meaningful states

# Part 5: Fetch API (3.6)

---

## Why We Are Using Fetch (Not XHR)

For this course flow, Fetch is the modern browser API to focus on.

- cleaner interface than XMLHttpRequest
- Promise-native behavior
- easier integration with async/await

We will skip AJAX/XHR implementation details today.

<!--
Lecture notes:
- Clarify: AJAX is concept; Fetch is the concrete API we implement.
-->

---

## Fetch Request Lifecycle

1. Build request URL/options
2. Call `fetch()`
3. Check response status
4. Parse JSON body
5. Update UI state
6. Handle failures and finalize

Treat status checking as required, not optional.

<!--
Lecture notes:
- Emphasize common beginner bug: assuming fetch rejects on 404/500.
-->

---

## Fetch Best Practices

- Validate and encode query parameters
- Check `response.ok` before parsing body
- Handle timeouts/cancellation strategy
- Keep fetch logic in service modules
- Return normalized data to components

<!--
Lecture notes:
- Remind students to keep fetch in service layer, not inside view rendering logic.
-->
