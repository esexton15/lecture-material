## What Node.js Is

Node.js is a JavaScript runtime for server-side code.

- Runs JavaScript outside the browser
- Gives access to files, processes, and networking
- Uses the V8 engine
- Supports event-driven, non-blocking I/O

Outcome: one language can now power both client and server.

<!--

## Why Node Fits This Course Sequence

Last lecture:

- client sends requests
- client manages loading, success, and error state

This lecture:

- server receives requests
- server validates data and selects a response
- server returns JSON or rendered HTML

Node lets the same JavaScript vocabulary span both sides.

## Node Modules and Project Structure

Node applications are built from modules.

- built-in modules for core features
- third-party packages installed with npm
- your own files for routes, controllers, and models

Good structure matters early because server code grows quickly.

# Part 2: Express and Request-Response Flow (4-4)

<!--
Instructor transition line:

## What Express Adds

Express is a lightweight framework built on top of Node's HTTP capabilities.

It gives you:

- routing by URL and HTTP method
- middleware for shared request processing
- easier request and response handling
- a cleaner path to APIs and server-rendered apps

Express removes boilerplate so your code focuses on behavior.

<!--
Lecture notes:
- Phrase to repeat: "Express is how we stop rewriting raw server plumbing."
-->

---

## The Request-Response Lifecycle

For each request:

1. Client sends a URL, method, and optional data
2. Express matches a route
3. Middleware and controller logic run
4. Data is validated and processed
5. Server sends back JSON, HTML, redirect, or error

This is the server-side mirror of the Fetch lifecycle from Lecture 5.

<!--
Lecture notes:
- Explicitly connect this slide to the earlier client lifecycle slide.
- Point to each step and map one real example request end-to-end before advancing.
-->

---

## Routes and HTTP Methods

Common route meanings:

- GET reads data
- POST creates data
- PUT updates data
- DELETE removes data

Each route combines:

- method
- path
- handler function

<!--
Lecture notes:
- Emphasize that a route is not just a URL; the HTTP method matters too.
- Quick check question: "What changes if I keep the same path but switch GET to POST?"
-->

---

## Request and Response Objects

The request object provides incoming data:

- req.params for path values
- req.query for query string values
- req.body for submitted content

The response object sends results back:

- res.json()
- res.send()
- res.status()
- res.render()

<!--
Lecture notes:
- Students do not need every property; they need the mental model of incoming data vs outgoing response.
-->

---

## Middleware as a Pipeline

Middleware runs in order while a request moves through the app.

Common uses:

- logging
- body parsing
- authentication checks
- validation and shared preprocessing

Middleware keeps repeated logic out of individual routes.

# Part 3: MVC Architecture (4-5)

<!--
Instructor transition line:
- "Our routes work, but now we need a structure that still works when the app doubles in size."
-->

---

## Why MVC Exists

As server code grows, mixing everything in one file becomes fragile.

MVC separates responsibilities:

- Model: data and business rules
- View: output presented to users
- Controller: request-handling workflow

Benefit: easier maintenance, testing, and reasoning.

<!--
Lecture notes:
- Stress that MVC is about separation of concerns, not academic complexity.
- Give one concrete pain point: "Single-file apps make bug tracing and team work harder."
-->

---

## Model Responsibilities

Models own data-related logic.

- data shape
- validation rules
- persistence or database access
- reusable business rules

Models should not care about HTTP details or page layout.

<!--
Lecture notes:
- Good phrase: "A model should make sense even if Express disappeared tomorrow."
-->

---

## Controller Responsibilities

Controllers coordinate the request lifecycle.

They usually:

1. read request data
2. validate or normalize input
3. call model logic
4. choose the response format
5. send success or error output

Controllers connect HTTP requests to application rules.

<!--
Lecture notes:
- This is the best place to reinforce workflow over syntax.
-->

---

## View Responsibilities

Views present information.

- server-side views render HTML templates
- API responses often act as a data view in JSON form
- client frameworks can also serve as the final presentation layer

In a full-stack app, the server may return JSON while the browser builds the visible UI.

<!--
Lecture notes:
- Clarify that "view" does not always mean a template file in modern apps.
-->

---

## MVC Request Flow

Typical sequence:

1. Route receives the request
2. Controller takes over
3. Controller calls the model
4. Model returns data or validation result
5. Controller selects a response view
6. Client receives JSON or HTML

MVC makes that flow easier to see and debug.

<!--
Lecture notes:
- You can sketch this on the board as Route -> Controller -> Model -> Controller -> Response.
-->

## What Full-Stack Means Here

Full-stack development means one feature crosses layers:

- client UI collects input
- client sends request with Fetch
- server route/controller processes request
- model applies rules or stores data
- server responds
- client updates the UI

One user action now spans the entire application.

<!--
Lecture notes:
- Keep this practical: students should think in terms of one feature traveling through the whole stack.
-->

## End-to-End Feature Flow

Example flow:

1. User submits a form in the browser
2. Client sends POST request with JSON
3. Express route forwards control to controller
4. Controller validates input and calls model logic
5. Server returns success or validation error
6. Client updates the page with the result

Reliable apps design all six steps intentionally.

<!--
Lecture notes:
- Emphasize that many bugs happen at the boundaries between steps, not inside one line of code.
-->

---

## Validation Across the Stack

Client validation helps with usability.

Server validation is still required because:

- requests can be malformed
- clients can be bypassed
- business rules must stay consistent

Best practice: client validates early, server validates authoritatively.

<!--
Lecture notes:
- Repeat this as a rule students should remember beyond this lecture.
- Scripted line: "Client validation improves experience; server validation protects system integrity."
-->

---

## Error Handling Across the Stack

Common error classes:

- client input errors
- missing routes or missing data
- server exceptions
- unexpected response shapes

Good systems make errors visible in the right layer:

- user-facing message in the UI
- technical details in logs
- status code in the HTTP response

<!--
Lecture notes:
- Connect back to Lecture 5: user-friendly errors are part of feature design, not an afterthought.
-->
