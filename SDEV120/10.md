# Part 1 — Introduction to UML

---

## What Is UML?

**UML** stands for **Unified Modeling Language**.

- A standardized visual language for modeling software systems
- Like blueprints for construction — UML provides a visual design before coding
- Used by software engineers, business analysts, and system architects
- Maintained by the Object Management Group (OMG)

UML is **not a programming language** — it is a **design and documentation** tool.

---

## Why Use UML?

UML helps teams:

- **Visualize** system design before writing code
- **Communicate** ideas clearly between technical and non-technical stakeholders
- **Document** system architecture for future reference
- **Detect problems** early in the design phase
- **Provide a standard** that any developer can read and understand

A well-drawn UML diagram can save hours of misunderstanding and rework.

---

## Types of UML Diagrams

UML diagrams fall into two broad categories:

**Structural Diagrams** — show the static structure of the system

**Behavioral Diagrams** — show the dynamic behavior of the system

Let's look at each category.

---

## Structural Diagrams

| Diagram                 | Purpose                                                |
| ----------------------- | ------------------------------------------------------ |
| **Class**               | Show classes, attributes, methods, and relationships   |
| **Object**              | Show specific instances of classes at a moment in time |
| **Component**           | Show how physical components are organized             |
| **Deployment**          | Show hardware/software and how they are distributed    |
| **Composite Structure** | Show the internal parts of a class                     |
| **Package**             | Show how UML elements are organized into groups        |

These describe **what** the system is made of.

---

## Behavioral Diagrams

| Diagram                  | Purpose                                                       |
| ------------------------ | ------------------------------------------------------------- |
| **Use Case**             | Show what the system does from the user's perspective         |
| **Activity**             | Show the flow of control through a process (like a flowchart) |
| **Sequence**             | Show interactions between objects over time                   |
| **Communication**        | Show message exchanges between objects                        |
| **State Machine**        | Show the states an object can be in and transitions           |
| **Timing**               | Show behavior of objects over a time period                   |
| **Interaction Overview** | Show a high-level view of interactions                        |

These describe **how** the system behaves.

---

## Which Diagrams Matter Most for This Course?

We will focus on a few key diagram types:

1. **Use Case Diagrams** — your assignment this module
2. **Class Diagrams** — foundational for object-oriented design
3. **Activity Diagrams** — similar to flowcharts, which you already know
4. **Sequence Diagrams** — useful for showing step-by-step interactions

You should be aware of the others, but these four will be the most practical for your work.

---

# Part 2 — Use Case Diagrams

---

## Learning Objectives

By the end of this section, you should be able to:

- Identify the key elements of a use case diagram
- Create a use case diagram for a given system
- Use Draw.io to build a use case diagram

---

## What Is a Use Case Diagram?

A **use case diagram** shows:

- **What** a system does (its functions)
- **Who** interacts with the system (actors)
- The **boundary** between the system and the outside world

It does NOT show:

- How the system works internally
- Step-by-step processes
- Technical implementation details

Think of it as the **table of contents** for what a system can do.

---

## Key Elements of a Use Case Diagram

A use case diagram has four main elements:

1. **System Boundary** — a rectangle that defines what is "inside" the system
2. **Actors** — stick figures or labeled boxes representing users or external systems
3. **Use Cases** — ovals describing a specific function or scenario
4. **Relationships** — lines connecting actors to use cases, and use cases to each other

---

## Actors

An **actor** is anyone or anything that interacts with the system.

- Represented as a **stick figure** (human actor) or a **rectangle** (external system)
- Placed **outside** the system boundary
- Can be a person, another system, a device, or even time

Examples:

| System       | Actors                                 |
| ------------ | -------------------------------------- |
| Online Store | Customer, Payment System, Admin        |
| ATM          | Bank Customer, Bank Server             |
| Library      | Patron, Librarian, Notification System |

---

## Use Cases

A **use case** is a specific function or scenario the system performs.

- Represented as an **oval** with a verb phrase inside
- Placed **inside** the system boundary
- Describes **what** happens, not **how**

Good use case names:

- "Check Out Book" (good — clear action)
- "Search Catalog" (good — clear action)
- "Database Query" (bad — too technical)
- "System" (bad — too vague)

---

## System Boundary

The **system boundary** defines the scope of the system you are modeling.

- Drawn as a **rectangle** around all use cases
- The system name goes at the top of the rectangle
- Actors are placed **outside** the boundary
- Use cases are placed **inside** the boundary

The boundary makes it clear: "Everything inside this box is what we are building. Everything outside is something else."

---

## Relationships Between Use Cases

Three key types of relationships:

1. **Association** — a solid line connecting an actor to a use case
   - Simply means "the actor interacts with this use case"

2. **«include»** — a dashed arrow from one use case to another
   - The base use case **always** includes the other
   - Example: "Checkout" always includes "Calculate Tax"

3. **«extend»** — a dashed arrow from one use case to another
   - The extending use case is **optional** or **conditional**
   - Example: "Checkout" may be extended by "Apply Coupon"

---

## «include» vs. «extend» — When to Use Each

**«include»** — Mandatory sub-flow

- The included use case is **always** executed as part of the base use case
- Arrow points FROM the base use case TO the included use case
- Use when a behavior is **required** and **reusable** across multiple use cases

**«extend»** — Optional or conditional sub-flow

- The extending use case is **sometimes** executed
- Arrow points FROM the extending use case TO the base use case
- Use when a behavior is **optional**, **alternative**, or triggered by a **condition**

---

## Example 1 — Online Shopping System

**Actors:** Customer, Admin, Payment System

**Use Cases:**

- Browse Products
- Add to Cart
- Remove from Cart
- Checkout
- Make Payment
- View Order History
- Manage Inventory
- Generate Reports

**Relationships:**

- Customer → Browse Products, Add to Cart, Remove from Cart, Checkout, View Order History
- Admin → Manage Inventory, Generate Reports
- Checkout «includes» Make Payment
- Payment System → Make Payment

---

## Draw.io — Step by Step

Follow these steps to create a use case diagram in Draw.io:

1. **Open Draw.io** — go to [app.diagrams.net](https://app.diagrams.net)
2. **Find UML shapes** — in the left menu, click "UML" to expand the shape library
3. **Draw the system boundary** — drag a "Rectangle" from General shapes, label it with your system name
4. **Add actors** — drag "Actor" (stick figure) from the UML library, place outside the boundary
5. **Add use cases** — drag "Use Case" (oval) from the UML library, place inside the boundary
6. **Connect actors to use cases** — use the line tool or drag from an actor to a use case
7. **Label everything** — double-click shapes to add text
8. **Add «include»/«extend»** — use dashed arrows and label them

---

## Draw.io — Tips for Clean Diagrams

- **Align shapes** — select multiple shapes, right-click, choose "Align"
- **Space evenly** — use "Distribute" to create even spacing
- **Use consistent fonts** — keep all text the same size and style
- **Keep it readable** — do not overcrowd the diagram
- **Use colors sparingly** — a little color helps group related elements
- **Export as PNG or PDF** — File > Export as

---

## Common Mistakes in Use Case Diagrams

1. **Putting too much detail inside a use case** — a use case is a summary, not a flowchart
2. **Confusing actors with use cases** — actors are outside the system; use cases are inside
3. **Forgetting the system boundary** — without it, the scope is unclear
4. **Connecting actors to other actors** — actors connect to use cases, not to each other
5. **Using technical jargon** — use case names should be in plain language
6. **Including implementation details** — "Validate Credit Card" is too specific; "Make Payment" is better

# Part 3 — Secure Programming

---

## Learning Objectives

By the end of this section, you should be able to:

- Describe why security practices are essential in programming
- Identify common secure programming practices
- Explain the goals of security testing
- Describe how security fits into the software development lifecycle

---

## Why Security Matters in Programming

Software vulnerabilities have real-world consequences:

- **Data breaches** — millions of user records exposed
- **Financial loss** — stolen funds, fraud, ransomware
- **Safety risks** — medical devices, vehicles, infrastructure
- **Reputation damage** — loss of customer trust
- **Legal liability** — regulations like GDPR, HIPAA, PCI-DSS

Security is not an afterthought. It must be part of the design from the beginning.

---

## The Threat Landscape

Common software vulnerabilities:

| Vulnerability             | Description                            | Example                           |
| ------------------------- | -------------------------------------- | --------------------------------- |
| **Injection**             | Attacker sends malicious data as input | SQL injection drops a database    |
| **Buffer Overflow**       | Data exceeds allocated memory          | Crashes or allows code execution  |
| **Weak Authentication**   | Poor password policies or storage      | Passwords stored in plain text    |
| **Insecure Data Storage** | Sensitive data not properly protected  | Credit card numbers in log files  |
| **Broken Access Control** | Users can access unauthorized data     | Regular user accesses admin panel |

These are preventable with secure programming practices.

---

## Secure Programming Practices

Five fundamental practices every programmer should follow:

1. **Input Validation** — never trust user input
2. **Principle of Least Privilege** — give code only the access it needs
3. **Defense in Depth** — multiple layers of security
4. **Secure Defaults** — systems should be secure out of the box
5. **Fail Securely** — when errors occur, deny access rather than allow it

Let's examine each one.

---

## Input Validation — The Most Critical Practice

**Never trust user input.** Always validate:

- **Type checks** — is the input the expected data type?
- **Range checks** — is the value within acceptable bounds?
- **Length checks** — is the input too long or too short?
- **Format checks** — does the input match the expected pattern?
- **Allowlist over blocklist** — only accept known-good values

Example — validating a test score:

```
if score < 0 or score > 100 then
    display "Error: Score must be between 0 and 100"
else
    // process the score
endif
```

---

## Principle of Least Privilege

Give your program — and each part of it — **only the permissions it needs**.

- A function that reads data should not also be able to delete data
- A user-facing module should not have admin-level database access
- A program should not run with root/administrator privileges unless absolutely necessary

If a vulnerability is exploited, least privilege limits the damage.

---

## Defense in Depth

Do not rely on a single security measure. Use **multiple layers**:

1. **Input validation** at the entry point
2. **Authentication** to verify identity
3. **Authorization** to verify permissions
4. **Encryption** to protect data in transit and at rest
5. **Logging and monitoring** to detect suspicious activity

If one layer fails, the next layer still provides protection.

---

## Secure Defaults

Systems should be **secure by default**:

- Default passwords should not exist — require the user to set one
- Features should be off unless explicitly enabled
- Error messages should not reveal system details to users
- Permissions should be restrictive by default

A user should have to **opt in** to less secure behavior, not opt out of it.

---

## Fail Securely

When an error occurs, the system should **deny access** by default:

- If authentication fails, deny access — do not fall through to an authenticated state
- If input validation fails, reject the input — do not process it anyway
- If a database connection fails, show a generic error — do not expose the connection string

The system should be more likely to **block a legitimate request** than to **allow a malicious one**.

---

## Secure Design Patterns

Patterns that promote security by design:

| Pattern                     | Principle                                       |
| --------------------------- | ----------------------------------------------- |
| **Fail-Safe Defaults**      | Default to the most secure option               |
| **Complete Mediation**      | Check every access, not just the first one      |
| **Open Design**             | Security should not depend on secrecy of design |
| **Separation of Privilege** | Require multiple conditions for access          |
| **Economy of Mechanism**    | Keep security design simple and small           |
| **Least Common Mechanism**  | Minimize shared channels between users          |

These patterns help you think about security during design, not just during testing.

---

## Building Security into the SDLC

Security should be present at **every phase** of the Software Development Lifecycle:

1. **Requirements** — define security requirements alongside functional ones
2. **Design** — apply secure design patterns, threat modeling
3. **Implementation** — follow secure coding practices, input validation
4. **Testing** — security testing, vulnerability scanning, penetration testing
5. **Deployment** — secure configuration, access controls
6. **Maintenance** — patch vulnerabilities, monitor for attacks

This is called **"shifting left"** — moving security earlier in the process where it is cheaper and easier to fix problems.

---

## Security Testing

**Security testing** is different from functional testing:

- Functional testing asks: "Does the system do what it should?"
- Security testing asks: "Can the system be made to do what it should not?"

Security testing is **adversarial** — you must think like someone trying to break the system.

---

## Goals of Security Testing

1. **Identify vulnerabilities** — find weaknesses before attackers do
2. **Verify security controls** — confirm that defenses work as intended
3. **Assess risk** — determine the potential impact of discovered vulnerabilities
4. **Ensure compliance** — meet regulatory and organizational requirements
5. **Build confidence** — assure stakeholders that the system is safe to deploy

---

## Types of Security Testing

| Type                       | Description                                               |
| -------------------------- | --------------------------------------------------------- |
| **Vulnerability Scanning** | Automated tools scan for known vulnerabilities            |
| **Penetration Testing**    | Simulated attacks by a security professional              |
| **Code Review**            | Manual or automated review of source code for weaknesses  |
| **Fuzz Testing**           | Send random, unexpected input to find crashes             |
| **Security Audits**        | Comprehensive review of policies, procedures, and systems |

Each type serves a different purpose. A thorough approach uses multiple types.

---

## Testing for Loopholes and Weaknesses

To find loopholes, think like an attacker:

- **What happens if I enter negative numbers?** (e.g., quantity = -1)
- **What happens if I enter extremely large values?** (buffer overflow)
- **What happens if I skip a required step?** (broken access control)
- **What happens if I enter SQL or HTML in a text field?** (injection)
- **What happens if I modify the URL or form data?** (parameter tampering)

Common weaknesses to test for (OWASP Top 10 at a high level):

- Broken authentication
- Injection flaws
- Sensitive data exposure
- XML external entities
- Broken access control
- Security misconfiguration
- Cross-site scripting (XSS)
- Insecure deserialization
- Using components with known vulnerabilities
- Insufficient logging and monitoring

# Part 4 — Ethics in IT

## Learning Objectives

---

## Why Do Programmers Need a Code of Ethics?

Software affects **real people** in **real ways**:

- A medical app with a bug could endanger lives
- A data breach could expose millions of people's private information
- An algorithm could discriminate against certain groups
- A voting system error could undermine democracy

With great power comes great responsibility. A code of ethics provides:

- **Guidance** — what to do when facing difficult decisions
- **Accountability** — standards to be held to
- **Trust** — assurance to the public that professionals act with integrity

---

## The ACM/IEEE Code of Ethics

The joint ACM/IEEE-CS Code of Ethics establishes eight principles:

1. **Contribute to society and to human well-being**
2. **Avoid harm** — do not cause injury or damage
3. **Be honest and trustworthy** — be truthful and transparent
4. **Be fair and act to not discriminate** — treat all people equally
5. **Respect the work required to produce new inventions** — honor intellectual property
6. **Respect privacy** — protect personal data
7. **Honor confidentiality** — protect sensitive information
8. **Strive for quality** — maintain professional competence

These principles apply to every IT professional, not just software developers.

---

## Ethical Dilemmas in Programming

Real-world scenarios where ethics and technology collide:

**Data Privacy vs. Convenience:**

- Should an app collect location data to provide better service?
- Who owns the data — the user or the company?

**Security vs. Usability:**

- Should a system require complex passwords that users will forget?
- How much friction is acceptable in the name of security?

---

## Ethical Dilemmas in Programming

**AI Bias:**

- If a hiring algorithm learns biased patterns from historical data, is that ethical?
- Who is responsible when an AI makes a discriminatory decision?

**Surveillance:**

- Should a company monitor employee emails to prevent data leaks?
- Where is the line between security and privacy?

---

## Your Ethical Obligations as an IT Professional

As someone entering the IT field, you should:

- **Protect user data** — collect only what you need, store it securely, delete it when no longer needed
- **Write secure code** — follow the practices we discussed earlier today
- **Be transparent** — tell users what your software does, especially with their data
- **Report vulnerabilities** — if you find a security flaw, report it responsibly
- **Refuse unethical requests** — if asked to write code that harms users or hides wrongdoing, push back
- **Keep learning** — security threats evolve, and so should your knowledge

Your **Discussion assignment** this week asks you to explore these ideas further. Take the time to think critically about the ethical obligations of IT professionals.
