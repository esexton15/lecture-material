# Part 1 — Review The Three Fundamental Structures

---

## Learning Objectives

By the end of this section, you should be able to:

- Identify the three fundamental control structures
- Explain why every problem can be solved using only these three structures
- Recognize structured and unstructured flowcharts

---

## The Three Fundamental Structures

Every logic problem can be solved using only three structures:

1. **Sequence** — steps execute one after another
2. **Selection** — a question determines which path to take
3. **Repetition (Loop)** — steps repeat while a condition is true

This is not a suggestion — it is a mathematical proof (Bohm-Jacopini Theorem, 1966).

---

## Sequence Structure

Steps execute in order, one after another, with no branching.

```
Step A
Step B
Step C
```

Pseudocode example:

```
num score
score = 0
display "Enter a score:"
input score
```

No decisions, no repetition — just a straight line.

---

## Selection Structure (IF-THEN-ELSE)

A condition is evaluated. One of two paths is taken.

```
          /-- Yes --> Process A
Question
          \-- No  --> Process B
```

Pseudocode example:

```
if score >= 60 then
    display "Pass"
else
    display "Fail"
endif
```

---

## Repetition Structure (Loop)

A condition is evaluated. While true, the body executes and control returns to the condition.

```
          /-- Yes --> Process A --\
Question <                      /
          \-- No ---------------/
```

Pseudocode example:

```
while count < 5
    display count
    count = count + 1
endwhile
```

---

## Why Structure Matters

Structured programs are:

- **Easier to read** — anyone can follow the logic
- **Easier to debug** — problems are isolated to one structure
- **Easier to maintain** — changes are localized
- **Easier to test** — each structure can be verified independently
- **Free of spaghetti code** — no tangled, unpredictable flow

---

## Quick Check

Which structure is shown in each case?

1. Read a name, read an address, display both.
2. If the temperature is above 90, turn on the AC.
3. Keep asking for input until the user enters "quit".
4. Calculate tax, then calculate total, then display the receipt.

Answers: 1 — Sequence, 2 — Selection, 3 — Repetition, 4 — Sequence

# Part 2 — Structured vs. Unstructured Flowcharts

---

## What Makes a Flowchart Structured?

A flowchart is **structured** if it follows these rules:

1. **Single entry** — each structure has exactly one entry point
2. **Single exit** — each structure has exactly one exit point
3. **No crossed lines** — flowlines never cross or merge unpredictably
4. **Proper nesting** — structures can be nested inside each other, but never overlap

If any rule is broken, the flowchart is **unstructured**.

---

## A Structured Flowchart Segment

```
            +----------+
            | Start    |
            +----+-----+
                 |
            +----v-----+
            | Process A|
            +----+-----+
                 |
            +----v-----+
            |  Is X>0? |
            +----+-----+
           Yes /    \ No
              /      \
    +--------v--+  +-v----------+
    | Process B  |  | Process C  |
    +--------+---+  +--------+---+
             \              /
              \            /
               v          v
            +----+-----+
            | Process D|
            +----+-----+
                 |
            +----v-----+
            | End      |
            +----------+
```

Clean paths. No crossing. Every structure enters and exits once.

---

## An Unstructured Flowchart Segment

```
            +----------+
            | Start    |
            +----+-----+
                 |
            +----v-----+
            |  Is A?   |
            +----+-----+
           Yes /    \ No
              /      \
    +--------v--+    |
    | Process B  |    |
    +--------+---+    |
             |        |
        +----v----+   |
        | Is C?   +---+---+
        +----+----+       |
       Yes /  \ No       |
          /    \         |
   +-----v-+ +-v-------+|
   |Proc D | |Proc E   ||
   +---+---+ +----+-----+|
       |          |       |
       v          v       |
   +---+----------+-------+---+
   |         Process F       |
   +---------+----+----------+
             |    |
             v    |
         +---+----+--+
         |   End    |
         +----------+
```

Lines cross. A "No" from C jumps past A. This is **spaghetti logic**.

---

## The Problem with Spaghetti Code

Unstructured programs:

- Are **hard to read** — you cannot easily trace the flow
- Are **hard to debug** — errors can hide in tangled paths
- Are **hard to modify** — a change in one spot breaks logic elsewhere
- Are **hard to test** — you cannot isolate a single path reliably
- Often produce **unpredictable results** — paths may never execute or may execute too many times

---

## Can Every Problem Be Solved Structured?

**Yes.**

The **Bohm-Jacopini Theorem** (1966) proved that any computable function can be implemented using only:

- Sequence
- Selection
- Repetition

No GOTO statements. No unrestricted jumps. No crossed lines.

If a flowchart is unstructured, it can always be rewritten to be structured — sometimes by **repeating steps**.

---

## The "Spaghetti Method"

The technique from your textbook (Appendix B) for converting an unstructured flowchart into a structured one:

1. Start at the **first decision** in the flowchart
2. Follow **one branch** at a time — imagine pulling on a strand of spaghetti
3. Document every process and decision along that path
4. When a path crosses another or loops back past a decision, **repeat the decision** to keep lines clean
5. Continue until all paths are straightened out

Key insight: **you may need to duplicate steps** to eliminate crossed lines.

---

## Spaghetti Method — Step 1: Start at the First Decision

Find the first evaluation symbol (diamond) in the unstructured flowchart.

- This must be the start of either a **selection** or a **loop**
- A sequence would not branch, so if there is a decision, it is selection or repetition
- Label it clearly — in the textbook example, this is **Decision A**

Everything after this decision must be restructured.

---

## Spaghetti Method — Step 2: Follow the "No" Branch

Pull on the "No" (or left) branch of the first decision.

- Trace every step along this path to the end
- Document each process in order
- In the textbook example (Figure B-3): Decision A → No → Process E → Process G → End

This becomes the **else branch** of your new selection structure.

---

## Spaghetti Method — Step 3: Follow the "Yes" Branch

Now pull on the "Yes" (or right) branch of the first decision.

- You encounter another decision — label it **Decision B**
- Follow B's "No" branch: Process D → Decision F
- Follow F's "No" branch: Process G → End
- Follow F's "Yes" branch: End

This is building the **then branch** of your selection, with nested selections inside.

---

## Spaghetti Method — Step 4: Handle Repeated Steps

Notice something important: **Process G now appears in two places**.

- Once on the "No" path from Decision A
- Once on the "No" path from Decision F

This is normal and expected. When restructuring:

- **Duplicating steps** is acceptable and often necessary
- The goal is clean structure, not minimal steps
- The program still produces the **same results**

---

## Spaghetti Method — Step 5: Identify Loops

The most challenging part of restructuring is handling loops.

A structured loop must look like this:

```
     +------+
     |Question|
     +---+--+
    Yes |  | No
        v  |
     +--------+
     | Process |
     +---+----+
         |
         +--> (back to Question)
```

The loop body must return **directly back to its own question** — never to a question above it.

---

## Spaghetti Method — Step 6: Repeat the Decision When Needed

If a loop in the original unstructured flowchart returns to a decision **above** its own question, you must **repeat that decision**.

From the textbook example:

- Process C leads back to Decision A (not to Decision B or C)
- But a structured loop must return to its own question
- Solution: **place a second copy of Decision A** after Process C

This creates a clean loop structure that preserves the original logic.

---

## Key Insight — Duplicating Steps Is Okay

When restructuring an unstructured flowchart:

- You will often **repeat processes** and **repeat decisions**
- This is the trade-off: slightly more steps in exchange for clean, readable, testable logic
- The restructured program performs **exactly the same tasks** as the original
- No behavior is lost — only spaghetti is removed

Think of it like untangling cords: you might need a longer cord, but at least you can see where everything goes.

---

## Worked Example — The Original Unstructured Chart

Consider this unstructured segment from your textbook (Figure B-1):

```
         Start
           |
         [A?]
        /     \
      Yes      No
       |        |
      [B?]      E
     /    \      |
   Yes     No    G
    |       |    |
    C       D   End
    |       |
    |      [F?]
    |     /    \
    |   No     Yes
    |   |       |
    +---G      End
        |
       End
```

Problems: G appears twice, C loops back past B to A, lines cross.

---

## Worked Example — Step 1: Pull the No Branch from A

Follow the left (No) branch from A:

```
if A is No then
    process E
    process G
    end
```

This is clean — it is a simple sequence. No restructuring needed on this path.

---

## Worked Example — Step 2: Pull the Yes Branch from A

Follow the right (Yes) branch from A:

```
else    // A is Yes
    if B is No then
        process D
        if F is No then
            process G
            end
        else    // F is Yes
            end
        endif
    endif
```

Notice: G appears again here. That is expected duplication.

---

## Worked Example — Step 3: Handle the Loop from C

The Yes branch of B leads to Process C, which loops back to A.

To make this structured, we place a **second copy of Decision A** after C:

```
else    // B is Yes
    process C
    if A is Yes then      // <-- repeated decision
        // loops back to process C
        process C
        if A is Yes then  // <-- repeated again
            ...
        endif
    else    // A is No
        // falls through
    endif
endif
```

This is now a **structured while loop**.

---

## Worked Example — Step 4: The Final Structured Version

```
while A is Yes
    if B is Yes then
        process C
        // loop back to A (handled by while)
    else    // B is No
        process D
        if F is Yes then
            // exit — set A to No or break
        else    // F is No
            process G
        endif
    endif
endwhile
process E
process G
```

Same behavior. Clean structure. No crossed lines.

---

## Before vs. After

**Before (Unstructured):**

- Crossed flowlines
- Multiple entry points to processes
- A loop that jumps past another decision
- Hard to trace, hard to modify

**After (Structured):**

- Clean nesting
- Every structure has one entry and one exit
- Loops return to their own condition
- Easy to read, test, and maintain

The price: a few duplicated steps. The reward: a program anyone can understand.

# Part 3 — Priming Input

---

## Learning Objectives

By the end of this section, you should be able to:

- Explain why a priming read is needed before a loop
- Write pseudocode that uses priming input with a sentinel value
- Identify common mistakes when using priming input

---

## The Priming Read Problem

Many programs need to **read input repeatedly** until a sentinel value is entered.

Consider: "Keep reading test scores until the user enters -1."

The loop condition checks the value. But where does the first value come from?

```
while score != -1
    // We need score to have a value BEFORE we check this condition
    process score
    input score
endwhile
```

**Problem:** The variable `score` has no value the first time the condition is evaluated.

---

## Example Without Priming — Logic Error

```
num score
num total = 0

while score != -1          // score is uninitialized!
    display "Enter a score:"
    input score
    total = total + score
endwhile
```

This is a **logic error**:

- `score` contains garbage or zero before the first check
- The condition may evaluate incorrectly on the first iteration
- Results are unpredictable

---

## Example With Priming — Correct Logic

```
num score
num total = 0

display "Enter a score (or -1 to quit):"
input score                      // <-- priming read

while score != -1
    total = total + score
    display "Enter a score (or -1 to quit):"
    input score                  // <-- read again inside loop
endwhile

display "Total:", total
```

The **priming read** gives `score` a valid value before the loop condition is ever checked.

---

## The Priming Input Pattern

The general pattern for priming input:

```
1. Read the first value              // PRIMING READ
2. While the value is not the sentinel
   a. Process the value
   b. Read the next value            // UPDATE READ
3. Continue with the rest of the program
```

Two reads are required:

- **One before the loop** (priming)
- **One at the end of the loop body** (updating for the next iteration)

---

## Sentinel Values and Priming

A **sentinel value** is a value that signals "stop processing."

- Must be a value that would **never** appear as valid data
- Common choices: -1, 0, 999, "QUIT", "end"

Examples:

| Application | Valid Data | Sentinel         |
| ----------- | ---------- | ---------------- |
| Test scores | 0–100      | -1               |
| Ages        | 1–120      | 0 or -1          |
| Prices      | > 0        | 0 or -1          |
| Names       | any string | "ZZZZ" or "quit" |

The priming read must read the first value before the loop checks for the sentinel.

---

## Common Mistakes with Priming Input

1. **Forgetting the priming read entirely** — the loop condition checks an uninitialized variable
2. **Reading input twice before the loop** — wastes the first value, skips data
3. **Forgetting the update read inside the loop** — infinite loop (the condition never changes)
4. **Choosing a sentinel that could be valid data** — the loop ends too early

---

## Practice — Priming Input

Write pseudocode for a program that:

- Reads product prices from a user

- Stops when the user enters 0 (the sentinel)
- Displays the final total


---

## Learning Objectives

---

## Integer vs. Floating-Point Values

Computers store numbers in two fundamental ways:

**Integers (whole numbers):**

- No decimal point
- Exact representation
- Examples: 0, 1, 42, -7, 1000
- Used for: counts, indexes, loop counters

**Floating-point (real numbers):**

- Has a decimal point
- Approximate representation (rounding is possible)
- Examples: 3.14, -0.5, 100.0, 2.0e10
- Used for: measurements, averages, currency calculations

---

## Integer Division vs. Floating-Point Division

This is a common source of bugs:

| Expression | Result | Type                |
| ---------- | ------ | ------------------- |
| 7 / 2      | 3.5    | Floating-point      |
| 7 // 2     | 3      | Integer division    |
| 7 % 2      | 1      | Modulus (remainder) |

In many languages, `7 / 2` gives **3** (integer division) if both operands are integers.

To get 3.5, at least one operand must be floating-point: `7.0 / 2` or `7 / 2.0`.

**Always know your language's rules.**

---

## Arithmetic Operators

The five fundamental arithmetic operators:

| Operator | Operation           | Example | Result |
| -------- | ------------------- | ------- | ------ |
| `+`      | Addition            | 5 + 3   | 8      |
| `-`      | Subtraction         | 10 - 4  | 6      |
| `*`      | Multiplication      | 6 \* 7  | 42     |
| `/`      | Division            | 15 / 4  | 3.75   |
| `%`      | Modulus (remainder) | 17 % 5  | 2      |

The **modulus operator** (`%`) returns the remainder after division — useful for checking even/odd, extracting digits, and cycling through values.

---

## Order of Operations

Programming follows the same order of operations as mathematics:

1. **Parentheses** — evaluated first, innermost first
2. **Multiplication, Division, Modulus** — left to right
3. **Addition, Subtraction** — left to right

Example:

```
2 + 3 * 4        = 2 + 12      = 14     (not 20)
(2 + 3) * 4      = 5 * 4       = 20
10 - 6 / 2 + 1   = 10 - 3 + 1  = 8
10 % 3 + 2 * 4   = 1 + 8       = 9
```

**When in doubt, use parentheses.** They cost nothing and make your intent clear.

---

## Type Coercion and Promotion

What happens when you mix integer and floating-point in an expression?

```
num wholeNumber = 5        // integer
num decimal = 2.5          // floating-point
num result

result = wholeNumber + decimal   // 5 + 2.5 = 7.5
```

Most languages **promote** the integer to floating-point before the operation.

The result is floating-point.

Be careful with the reverse:

```
num result = 7.9 / 2      // 3.95
num truncated = 7.9 / 2    // depends on variable type
```

If `truncated` is an integer, the value **3.95** is stored as **3** — data is lost.

---

## Practical Example — Area of a Circle

```
num radius
num area
num pi = 3.14159

display "Enter the radius:"
input radius

area = pi * radius * radius

display "The area is:", area
```

If `radius` is entered as `5`, the result is `78.53975`.

If `pi` and `radius` were both integers, the result would be **75** — incorrect.

---

## Practical Example — Temperature Conversion

Convert Fahrenheit to Celsius: **C = (F - 32) \* 5 / 9**

```
num fahrenheit
num celsius

display "Enter temperature in Fahrenheit:"
input fahrenheit

celsius = (fahrenheit - 32) * 5 / 9

display "Celsius:", celsius
```

Test: F = 212 → C = (180) \* 5 / 9 = 900 / 9 = **100** (boiling point)

Note: Parentheses around `(fahrenheit - 32)` are essential.

---

## Practical Example — Payroll Calculation

```
num hoursWorked
num hourlyRate
num regularPay
num overtimePay
num grossPay

display "Enter hours worked:"
input hoursWorked
display "Enter hourly rate:"
input hourlyRate

if hoursWorked <= 40 then
    regularPay = hoursWorked * hourlyRate
    overtimePay = 0
else
    regularPay = 40 * hourlyRate
    overtimePay = (hoursWorked - 40) * hourlyRate * 1.5
endif

grossPay = regularPay + overtimePay
display "Gross pay:", grossPay
```
